Βασικές Μέθοδοι του Package strings

Συνάρτηση (Function) Περιγραφή (Description) Παράδειγμα (Example)
strings.Fields(s) Χωρίζει το string σε slice λέξεων, αγνοώντας πολλαπλά κενά, tabs & newlines. strings.Fields(" a b ") ➔ ["a", "b"]
strings.Join(slice, sep) Ενώνει ένα slice από strings με ένα συγκεκριμένο διαχωριστικό ανάμεσά τους. strings.Join(w, " ") ➔ "hello world"
strings.Split(s, sep) Χωρίζει το string σε slice βάσει αυστηρού separator (π.χ. κόμμα ή άνω κάτω τελεία). strings.Split("a,b,c", ",") ➔ ["a","b","c"]

strings.Trim(s, cutset) Αφαιρεί οποιονδήποτε χαρακτήρα του `cutset` από την αρχή και το τέλος του string. strings.Trim(" 'hello' ", " '") ➔ "hello"
strings.TrimSpace(s) Αφαιρεί όλα τα whitespace κενά από την αρχή και το τέλος του string. strings.TrimSpace(" text ") ➔ "text"
strings.HasPrefix / HasSuffix Ελέγχει αν το string ξεκινάει ή τελειώνει με συγκεκριμένο πρόθεμα/επίθεμα. strings.HasSuffix(w, ":") ➔ true
strings.ReplaceAll(s, old, new) Αντικαθιστά όλες τις εμφανίσεις ενός substring χωρίς το overhead της regex. strings.ReplaceAll(s, " ,", ", ")

Γράφοντας ένα Test στην Πράξη: ToUppercase

Όλα όσα πρέπει να γνωρίζεις για ένα idiomatic Go Unit Test:

1. ΥΠΟΓΡΑΦΗ: (t *testing.T)

Κάθε test ξεκινά με Test... και δέχεται υποχρεωτικά t *testing.T. Μέσω αυτού καλούμε t.Errorf() για αναφορά αποτυχίας χωρίς άμεσο τερματισμό.

2. ΕΠΩΝΥΜΟ STRUCT (ΟΧΙ ΑΝΩΝΥΜΟ)

Ορίζουμε ρητά type TestCase struct με πεδία name, input, expected. Αποφεύγουμε ανώνυμα structs ώστε ο κώδικας να είναι απόλυτα ευανάγνωστος.

3. ΤΙ ΔΕΧΕΤΑΙ ΤΟ t.Run(name, f)

• name string: Το όνομα του sub-test (εμφανίζεται αναλυτικά στο go test -v).
• f func(t *testing.T): Η συνάρτηση που εκτελεί τον έλεγχο.

TDD FLOW: Γράφεις πρώτα το test (FAIL) ➔ Υλοποιείς τη function ➔ go test -v (PASS)
// 1. Επώνυμο struct για τα test cases (όχι inline ανώνυμο) type TestCase struct { name string input string expected string } // 2. Το Unit Test που γράφουμε ΠΡΩΤΑ (Red Phase) func TestToUppercase(t *testing.T) { cases := []TestCase{ {name: "simple word", input: "hello", expected: "HELLO"}, {name: "already upper", input: "GO", expected: "GO"}, {name: "empty string", input: "", expected: ""}, } for _, tc := range cases { // t.Run δέχεται: (name string, f func(t *testing.T)) t.Run(tc.name, func(t *testing.T) { got := ToUppercase(tc.input) if got != tc.expected { t.Errorf("got %q, want %q", got, tc.expected) } }) } } // 3. Η συνάρτηση που γράφουμε ΜΕΤΑ για να περάσει το test (Green Phase) func ToUppercase(s string) string { return strings.ToUpper(s) }

ARCHITECTURAL COMPARISON // RATIONALE

Πολλά Περάσματα vs Buffer/FSM: Τεχνική Ανάλυση

Διάσπαση σε επιμέρους υποπροβλήματα (Divide & Conquer).

  • Multi-Pass (Απομονωμένα Στάδια): Κάθε στάδιο αναλαμβάνει έναν μετασχηματισμό. Εάν υπάρξει σφάλμα στα εισαγωγικά, η διερεύνηση περιορίζεται αποκλειστικά στη συγκεκριμένη συνάρτηση.
  • Single-Pass Buffer: Ένα πέρασμα με buffer ολίσθησης. Απαιτεί ταυτόχρονο συγχρονισμό πολλαπλών σημαιών κατάστασης (inQuotes, modifierCount, pendingPunctuation).
  • Γνωστικό Φορτίο: Το multi-pass μειώνει δραστικά την πιθανότητα απρόβλεπτων παρενεργειών μεταξύ κανόνων.
TRADE-OFF MATRIX // TECHNICAL SELECTION

Πεδία Εφαρμογής & Trade-offs

PIPELINE (MULTI-PASS)

Πλεονεκτήματα Pipeline

  • Απομόνωση Σφαλμάτων: Κάθε στάδιο ελέγχεται πλήρως ανεξάρτητα με unit tests
  • Απλότητα Debugging: Άμεση επιθεώρηση ενδιάμεσου string μεταξύ των σταδίων
  • Ταχύτητα Ανάπτυξης: Σαφής διαχωρισμός σε επιμέρους task cards
  • Κόστος: Δημιουργία ενδιάμεσων strings στη μνήμη (αμελητέο για αρχεία < 10MB)
BUFFER / FSM (SINGLE-PASS)

Πλεονεκτήματα Single-Pass FSM

  • Διαχείριση Μεγάλων Αρχείων: Επεξεργασία gigabytes χωρίς φόρτωση όλου του αρχείου στη RAM
  • Μηδενικές Κατανομές (Zero Allocations): Εγγραφή απευθείας στον output buffer
  • Συστήματα Χαμηλού Επιπέδου: Κατάλληλο για embedded firmware και network drivers
  • Κόστος: Υψηλή πολυπλοκότητα στη διαχείριση σύνθετων μεταβάσεων κατάστασης

PROCESS & TOOLS // METHODOLOGY

Task Cards & Καταγραφή Χρήσης AI

Δομή Task Cards (tasks/TASK-XX.txt)

  • Goal: Τι ακριβώς αλλάζει μόλις ολοκληρωθεί η εργασία.
  • Depends on: Προηγούμενες εργασίες από τις οποίες εξαρτάται.
  • Acceptance Criteria: Μετρήσιμο αποτέλεσμα ολοκλήρωσης.
  • Tests to Write First: Ονόματα tests που αποδεικνύουν τη λειτουργία.
  • Notes: Ειδικές περιπτώσεις ή τεχνικές παρατηρήσεις.
AI USAGE LOGGING PROTOCOL

Αρχείο καταγραφής στο αποθετήριο: ai/task-decomposition-index.txt

  • Εργαλείο / Μοντέλο: Έκδοση και ημερομηνία αλληλεπίδρασης.
  • Αίτημα (Prompt): Τι ακριβώς ζητήθηκε από το AI.
  • Αξιολόγηση Εξόδου: Τι διατηρήθηκε και τι τροποποιήθηκε στον κώδικα.
  • Συσχέτιση: Ποιο συγκεκριμένο Task Card επηρεάστηκε.
  • Επεξηγησιμότητα: Πλήρης κατανόηση κάθε γραμμής κώδικα κατά το audit.
QUALITY GATE // PEER AUDIT

Κριτήρια Αξιολόγησης Peer Audit (Phase 2 Gate)

Rubric Αξιολόγησης (0-2 βαθμοί ανά πεδίο, σύνολο /10):

  • 1. Problem & functions clarity: Πλήρης κατανόηση και διατύπωση των 7 κανόνων.
  • 2. Architecture rationale: Τεκμηριωμένη επιλογή Pipeline έναντι FSM.
  • 3. Test coverage & originality: 4 audit cases συν πρωτότυπα edge cases.
  • 4. Reproducibility & organization: Καθαρή δομή φακέλων και αρχείων.
  • 5. Task decomposition clarity: 5-8 ελέγξιμες εργασίες με σαφή κριτήρια.
REPORT: audit/peer-audit-YYYY-MM-DD-<auditor>.txt
Problem & functions clarity ➔ <0|1|2>
Architecture rationale (Pipeline vs FSM) ➔ <0|1|2>
Test coverage & originality ➔ <0|1|2>
Reproducibility & organization ➔ <0|1|2>
Task decomposition clarity & testability ➔ <0|1|2>

Outcome: <Accept|Reject> (Score >= 8/10)

Η συγγραφή κώδικα υλοποίησης ξεκινά μόνο μετά από επίσημο Accept στο report.

TECHNICAL DISCUSSION // OPEN FLOOR

Θέματα Τεχνικής Συζήτησης

Βασικά ερωτήματα προς τεκμηρίωση στο PRD:

  • Επιλογή Αρχιτεκτονικής: Ποια αρχιτεκτονική επιλέξατε (Pipeline ή FSM) και ποια συγκεκριμένα trade-offs αποδεχτήκατε;
  • Σειρά Μετασχηματισμών: Ποια είναι η ακριβής σειρά εκτέλεσης των κανόνων και πώς αποτρέπονται ανεπιθύμητες αλληλεπιδράσεις;
  • Σχεδίαση Edge Cases: Ποιες οριακές καταστάσεις εκτός των audit cases έχετε συμπεριλάβει στα tests σας;
