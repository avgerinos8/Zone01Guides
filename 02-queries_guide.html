Εισαγωγή στα Queries: Από το Μηδέν

Όταν ακούμε τον όρο "Βάση Δεδομένων" (Database), το μυαλό μας συχνά πάει σε πολύπλοκα συστήματα. Στην πραγματικότητα, η κεντρική ιδέα είναι εξαιρετικά απλή.

Φαντάσου ένα αρχείο Excel. Σε αυτό το αρχείο, έχεις διάφορα "Φύλλα" (Sheets). Κάθε φύλλο έχει Στήλες (π.χ. Όνομα, Ηλικία, Email) και Γραμμές (κάθε γραμμή είναι και ένας διαφορετικός άνθρωπος).

Μια Σχεσιακή Βάση Δεδομένων είναι πρακτικά μια εξελιγμένη, ταχύτατη μορφή αυτού του Excel. Τα "Φύλλα" τα ονομάζουμε Πίνακες (Tables). Τις "Γραμμές" τις ονομάζουμε Εγγραφές (Rows) και τις "Στήλες" τις ονομάζουμε Πεδία (Columns).

Τι γίνεται όμως όταν το Excel σου αποκτήσει 10 εκατομμύρια γραμμές και θέλεις να βρεις "όλους τους χρήστες άνω των 18 που το email τους λήγει σε @gmail.com"; Εκεί το Excel "κολλάει". Εκεί χρειαζόμαστε τα Queries.

Τι ακριβώς είναι ένα Query;

Η λέξη Query σημαίνει "Ερώτημα". Είναι μια εντολή που δίνουμε στη Βάση Δεδομένων για να κάνει μία από τις εξής τέσσερις βασικές δουλειές (γνωστές και ως CRUD):

  • Create: Να δημιουργήσει/εισάγει νέα δεδομένα.
  • Read: Να διαβάσει/αναζητήσει υπάρχοντα δεδομένα.
  • Update: Να ενημερώσει/αλλάξει δεδομένα που ήδη υπάρχουν.
  • Delete: Να διαγράψει δεδομένα.

Για να "μιλήσουμε" στη Βάση, χρησιμοποιούμε μια ειδική, πολύ απλή γλώσσα που ονομάζεται SQL (Structured Query Language). Διαβάζεται σχεδόν σαν απλά Αγγλικά!

-- Select (Read) all columns (*) from the 'users' table
-- where the age is greater than 18.
SELECT * FROM users WHERE age > 18;

Αυτό είναι ένα Query! Ζητάει συγκεκριμένα δεδομένα με βάση κάποιους κανόνες (φίλτρα).

Κλειδιά: Πώς ξεχωρίζουμε τα δεδομένα

Σε έναν πίνακα, χρειαζόμαστε έναν τρόπο να ξεχωρίζουμε κάθε εγγραφή (γραμμή) με απόλυτη βεβαιότητα. Δύο χρήστες μπορεί να λέγονται "Γιώργος", αλλά είναι διαφορετικά άτομα.

Για αυτόν τον λόγο, εισάγουμε το Primary Key (Πρωτεύον Κλειδί). Συνήθως είναι ένας αριθμός (ID) που είναι μοναδικός για κάθε γραμμή. Κανένας άλλος χρήστης δεν μπορεί να έχει το ID `5`.

Σχεσιακές Βάσεις (Relational): Το μεγάλο τους ατού είναι ότι οι Πίνακες μπορούν να συνδέονται. Για παράδειγμα, αν έχουμε έναν πίνακα `posts` και έναν πίνακα `reactions`, στο `reactions` δεν γράφουμε ξανά το όνομα του χρήστη. Γράφουμε απλά το ID του χρήστη (αυτό λέγεται Foreign Key - Ξένο Κλειδί). Έτσι "συσχετίζουμε" την αντίδραση με τον χρήστη που την έκανε.

// ── Table Structure Concept ───────────────────────────────────────────── ⊃
// Table: users
// ID (Primary Key) | Name
// 1                | Alice
// 2                | Bob

// Table: reactions
// user_id (Foreign) | post_id | value
// 1                 | 42      | like
// 2                 | 42      | dislike

Checkpoint 1: Βασικές Έννοιες

Τι ακριβώς πετυχαίνει η χρήση ενός Foreign Key (Ξένου Κλειδιού) σε μια βάση δεδομένων;
Επιτρέπει στη βάση δεδομένων να δημιουργεί αυτόματα μοναδικούς αύξοντες αριθμούς για κάθε νέα εγγραφή που προστίθεται σε έναν πίνακα.
Δημιουργεί μια εννοιολογική "γέφυρα" που συνδέει μια εγγραφή ενός πίνακα με μια συγκεκριμένη εγγραφή σε έναν άλλο, αποφεύγοντας την επανάληψη δεδομένων.
Κλειδώνει προσωρινά τη γραμμή δεδομένων ώστε να μην μπορεί να τροποποιηθεί από άλλους χρήστες κατά τη διάρκεια ενός ενεργού Query.
Σωστό! Το Ξένο Κλειδί (όπως το `user_id` στον πίνακα αντιδράσεων) δείχνει στο Πρωτεύον Κλειδί ενός άλλου πίνακα (όπως το `id` στον πίνακα χρηστών). Έτσι συνδέουμε δεδομένα χωρίς να αντιγράφουμε το όνομα του χρήστη παντού (επιλογή 1 περιγράφει το Auto-Increment, επιλογή 3 περιγράφει το Row Locking).

Τροποποίηση Δεδομένων (DML)

Ας δούμε πώς "γράφουμε" στη βάση (Data Manipulation Language). Οι τρεις βασικές εντολές είναι το `INSERT`, το `UPDATE` και το `DELETE`.

-- Insert a new row into the table.
INSERT INTO reactions (user_id, post_id, value) 
VALUES (1, 42, 'like');

-- Update existing data: change the value where conditions are met.
UPDATE reactions 
SET value = 'dislike' 
WHERE user_id = 1 AND post_id = 42;

-- Delete data entirely.
DELETE FROM reactions WHERE user_id = 1;

Πρόσεξε πολύ το `WHERE` στο `UPDATE` και στο `DELETE`. Αν το ξεχάσεις (π.χ. γράψεις σκέτο `UPDATE reactions SET value = 'like'`), όλες οι γραμμές του πίνακα θα αλλάξουν! Το `WHERE` είναι το "φίλτρο" μας.

Το πρόβλημα του "Set or Replace" (UPSERT)

Στη λογική της άσκησής σου, θέλουμε ο χρήστης να έχει ακριβώς μία αντίδραση ανά post. Αν κάνει 'like', μπαίνει νέο like. Αν μετά κάνει 'dislike', το προηγούμενο 'like' πρέπει να αντικατασταθεί. Δεν θέλουμε δύο εγγραφές.

Μια προφανής λύση στον κώδικά μας θα ήταν να κάνουμε 2 Queries: Πρώτα να ρωτήσουμε (SELECT) αν υπάρχει εγγραφή. Αν ναι, κάνουμε UPDATE. Αν όχι, κάνουμε INSERT.

Αυτό είναι ΛΑΘΟΣ στον προγραμματισμό βάσεων (Race Condition)! Τι γίνεται αν δύο αιτήματα φτάσουν στο server την ίδια ακριβώς χιλιοστή του δευτερολέπτου; Και τα δύο θα κάνουν SELECT, θα δουν ότι δεν υπάρχει εγγραφή, και θα κάνουν και τα δύο INSERT. Αποτέλεσμα: Διπλοτυπία.

Χρειαζόμαστε μια Ατομική (Atomic) λειτουργία που να τα κάνει όλα σε ένα βήμα. Στην SQLite, αυτό λύνεται κομψά με το UPSERT (Update or Insert):

-- Standard SQL way to handle conflicts (UPSERT)
-- 'UNIQUE' constraint must exist on (user_id, post_id) for this to trigger.
INSERT INTO reactions (user_id, post_id, value)
VALUES (1, 42, 'like')
ON CONFLICT (user_id, post_id) DO UPDATE SET value = 'like';

Checkpoint 2: Ατομικότητα (Atomicity) & UPSERT

Γιατί θεωρείται "επικίνδυνο" να ελέγξουμε με κώδικα (π.χ. σε Go) αν υπάρχει μια εγγραφή (SELECT) και αμέσως μετά να κάνουμε INSERT ή UPDATE ανάλογα με το αποτέλεσμα, αντί να χρησιμοποιήσουμε μια SQL εντολή UPSERT;
Επειδή ανάμεσα στον έλεγχο (SELECT) και την εγγραφή (INSERT/UPDATE), μια άλλη διεργασία μπορεί να τροποποιήσει τη βάση, προκαλώντας καταστάσεις συναγωνισμού (race conditions).
Επειδή η κλήση πολλαπλών ερωτημάτων (SELECT ακολουθούμενο από INSERT) καταναλώνει υπερβολική μνήμη RAM στον database server και οδηγεί σε κρασαρίσματα αν οι χρήστες είναι πολλοί.
Επειδή τα σύγχρονα συστήματα βάσεων δεδομένων απαγορεύουν από τον σχεδιασμό τους την εκτέλεση εντολών SELECT και INSERT μέσα στην ίδια σύνδεση (database connection).
Σωστό! Αυτό ονομάζεται "Race Condition" ή TOCTOU (Time of Check to Time of Use). Δύο ταυτόχρονα αιτήματα μπορεί να διαβάσουν την ίδια παλιά κατάσταση πριν προλάβει κάποιο να γράψει. Μια ατομική λειτουργία σε επίπεδο βάσης (όπως το ON CONFLICT) εγγυάται ότι η αλλαγή θα γίνει χωρίς παρεμβολές.

Συγκεντρωτικοί Υπολογισμοί (Aggregations)

Συχνά δεν θέλουμε τα ίδια τα δεδομένα, αλλά μια σύνοψη τους. Η SQL διαθέτει συναρτήσεις άθροισης (Aggregate Functions) όπως `COUNT()`, `SUM()`, `AVG()` κ.α.

Η πιο χρήσιμη είναι η `COUNT()`. Μετράει πόσες γραμμές ικανοποιούν το κριτήριο μας.

-- Count how many reactions post 42 has in total
SELECT COUNT(*) FROM reactions WHERE post_id = 42;

-- Count only the likes for post 42
SELECT COUNT(*) FROM reactions 
WHERE post_id = 42 AND value = 'like';

Πώς μπορούμε όμως να πάρουμε Ταυτόχρονα (σε ένα query) και τα likes και τα dislikes για να γλιτώσουμε χρόνο (roundtrips) στη βάση;

Conditional Aggregations (Υπό Συνθήκη Καταμέτρηση)

Μπορούμε να συνδυάσουμε συναρτήσεις στη βάση δεδομένων. Μπορούμε να βάλουμε λογική if-else (στην SQL λέγεται CASE WHEN) μέσα στο COUNT ή στο SUM!

-- Conditional counting in a single query
SELECT 
    SUM(CASE WHEN value = 'like' THEN 1 ELSE 0 END) as likes,
    SUM(CASE WHEN value = 'dislike' THEN 1 ELSE 0 END) as dislikes
FROM reactions 
WHERE post_id = 42;

Πώς λειτουργεί: Για κάθε εγγραφή του post 42, ελέγχει την τιμή. Αν είναι 'like', προσθέτει 1 στη στήλη "likes" και 0 στα dislikes. Αν είναι 'dislike', κάνει το αντίθετο. Στο τέλος το SUM μας δίνει τα συνολικά αθροίσματα, με ένα μόνο Query, ταχύτατα!

Αυτό είναι ιδανικό για την υλοποίηση της count() συνάρτησης στην άσκησή σου.

Checkpoint 3: Aggregations

Όταν χρησιμοποιούμε τη σύνταξη SUM(CASE WHEN συνθήκη THEN 1 ELSE 0 END) μέσα σε ένα SELECT, τι ακριβώς πετυχαίνουμε λειτουργικά;
Εξάγουμε από τη βάση δεδομένων όλες τις γραμμές που ικανοποιούν τη συνθήκη ως μια λίστα, προκειμένου να τις μετρήσουμε αργότερα στον κώδικα της Go.
Αυξάνουμε (κάνουμε Update) έναν εσωτερικό μετρητή στον πίνακα της βάσης κάθε φορά που κάποιος χρήστης προσθέτει ένα νέο like ή dislike.
Αξιολογούμε κάθε γραμμή ξεχωριστά, μετατρέποντας τη συνθήκη σε μια αριθμητική τιμή (0 ή 1), την οποία η βάση αθροίζει τελικά για να μας δώσει το συνολικό πλήθος.
Σωστό! Η αξιολόγηση (mapping) γίνεται γραμμή-γραμμή. Αν η συνθήκη ισχύει, η γραμμή "μεταφράζεται" σε 1, αλλιώς σε 0. Στη συνέχεια, η εξωτερική συνάρτηση SUM προσθέτει αυτούς τους άσους και τα μηδενικά, δίνοντάς μας τον αριθμό των γραμμών που ικανοποιούν τη συνθήκη, χωρίς να χρειαστεί να φέρουμε τα δεδομένα στον κώδικά μας (Go) για καταμέτρηση (όπως λέει λανθασμένα η επιλογή 1).

Συναλλαγές (Transactions): Όλα ή Τίποτα

Η άσκησή σου αναφέρει ρητά: "Use a database/sql transaction to preserve the rule..." και "Until a replacement commits, other operations must continue to see the previous row".

Τι είναι το Transaction; Είναι μια ομάδα από SQL εντολές που εκτελούνται ως ένα ενιαίο, αδιαίρετο μπλοκ. Είτε θα πετύχουν όλες (Commit), είτε, αν έστω και μία αποτύχει (ή αν πέσει το ρεύμα!), καμία δεν θα αποθηκευτεί και η βάση θα επιστρέψει στην αρχική της κατάσταση (Rollback).

// ── Go Transaction Pattern ────────────────────────────────────────────── ⊃
tx, err := db.Begin() // Start Transaction
if err != nil { return err }

// Execute query on the TRANSACTION object (tx), NOT the db object!
_, err = tx.Exec("UPDATE ...") 
if err != nil {
    tx.Rollback() // Undo everything!
    return err
}

err = tx.Commit() // Save permanently

Αυτή η απομόνωση (Isolation) είναι που εγγυάται ότι αν το replacement αποτύχει, η προηγούμενη αντίδραση θα μείνει άθικτη.

Οι αρχές A.C.I.D.

Τα σύγχρονα RDBMS (συμπεριλαμβανομένης της SQLite) υπακούουν σε 4 αυστηρούς κανόνες, γνωστούς ως ACID:

  • A - Atomicity (Ατομικότητα): Το "Όλα ή Τίποτα" που περιγράψαμε. Μια συναλλαγή δεν μένει ποτέ "μισοτελειωμένη".
  • C - Consistency (Συνέπεια): Μια συναλλαγή φέρνει τη βάση από μια έγκυρη κατάσταση σε μια άλλη έγκυρη κατάσταση (π.χ. σεβόμενη τα Constraints και τα Foreign Keys).
  • I - Isolation (Απομόνωση): Πολλαπλές συναλλαγές που γίνονται ταυτόχρονα, δεν βλέπει η μία την ημιτελή δουλειά της άλλης (Dirty Reads). Γι' αυτό οι άλλοι χρήστες συνεχίζουν να βλέπουν το παλιό 'like' μέχρι να γίνει `Commit` το 'dislike'.
  • D - Durability (Ανθεκτικότητα): Μόλις γίνει `Commit`, τα δεδομένα είναι γραμμένα μόνιμα στον δίσκο. Ακόμα και αν κοπεί το ρεύμα την επόμενη στιγμή, τα δεδομένα σώθηκαν.

Checkpoint 4: Transactions

Σύμφωνα με την ιδιότητα της Απομόνωσης (Isolation) στο μοντέλο ACID, τι συμβαίνει όταν η Συναλλαγή Α (Transaction A) τροποποιεί μια γραμμή, αλλά πριν κάνει Commit, μια Συναλλαγή Β ζητήσει να διαβάσει την ίδια γραμμή;
Η Συναλλαγή Β θα διαβάσει τα νέα δεδομένα που έγραψε η Συναλλαγή Α, διότι τα δεδομένα μπαίνουν αμέσως στην προσωρινή μνήμη (RAM) της βάσης για βελτίωση της ταχύτητας.
Η Συναλλαγή Β θα διαβάσει την παλιά έκδοση της γραμμής (αυτή που υπήρχε πριν ξεκινήσει η Συναλλαγή Α), ώστε να μην επηρεαστεί από αλλαγές που δεν έχουν οριστικοποιηθεί.
Η Συναλλαγή Β θα απορριφθεί αυτόματα με μήνυμα σφάλματος, επειδή απαγορεύεται αυστηρά η ανάγνωση δεδομένων που εμπλέκονται σε οποιαδήποτε ενεργή διαδικασία.
Σωστό! Αυτό είναι το νόημα του Isolation. Μέχρι να γίνει Commit (οριστικοποίηση), η μερική δουλειά του Transaction A είναι "αόρατη" στους υπολοίπους. Αυτό αποτρέπει τα λεγόμενα "Dirty Reads", δηλαδή το να διαβάσει κάποιος δεδομένα που τελικά ακυρώθηκαν (έγιναν Rollback). Η επιλογή 3 είναι λάθος γιατί η βάση δεν απορρίπτει το αίτημα, απλά σερβίρει την παλιά έγκυρη κατάσταση.

Συμβουλές Σχεδίασης στη Go (database/sql)

Για την άσκησή σου, υπάρχουν μερικά "κρυφά" σημεία στο πακέτο `database/sql` της Go που πρέπει να γνωρίζεις:

  • Το `*sql.DB` είναι ένα Pool: Δεν είναι μια απλή σύνδεση, αλλά μια δεξαμενή από συνδέσεις. Μπορεί να διαχειριστεί concurrent requests από μόνο του (είναι goroutine-safe).
  • `QueryRow` vs `Query`: Όταν περιμένεις ακριβώς μία γραμμή ως απάντηση (π.χ. στο `count()`), χρησιμοποίησε το `db.QueryRow()`. Αυτό αποθηκεύει τα δεδομένα απευθείας στις μεταβλητές σου μέσω του `.Scan(&likes, &dislikes)`.
  • Το Isolation στην SQLite: Η SQLite λειτουργεί παραδοσιακά "κλειδώνοντας" όλο το αρχείο σε Writes. Αν αρχίσεις ένα Transaction με σκοπό να γράψεις (Write), κλειδώνει τη βάση. Αυτό εγγυάται ακριβώς τη συμπεριφορά ατομικότητας που ζητάει η άσκηση (καμία επικάλυψη στις εγγραφές).

🏆 Τελικό Συνδυαστικό Quiz (Final Assessment)

Ώρα να συνδυάσουμε όλα όσα μάθαμε! Πρόσεξε καλά τις επιλογές.

Έχεις τη συνάρτηση setReaction. Αντί να χρησιμοποιήσεις Transactions ή UPSERT SQL logic, επιλέγεις να γράψεις τον κώδικα κάνοντας πρώτα `db.Query()` για έλεγχο και μετά `db.Exec()` για Update/Insert. Ποιος είναι ο κύριος λόγος που αυτή η σχεδίαση αποτυγχάνει στους κανόνες της άσκησης;
Ο κώδικας της Go είναι πιο αργός από τον κώδικα SQL, συνεπώς το πρόγραμμα θα απορριφθεί λόγω κακής απόδοσης στο parsing των δεδομένων.
Η βάση δεδομένων SQLite επιτρέπει μόνο ένα ενεργό Query ανά αρχείο, οπότε η κλήση του `Exec()` θα αποτύχει εάν το αποτέλεσμα του `Query()` δεν κλείσει (close) σωστά.
Εάν δύο ταυτόχρονες κλήσεις της συνάρτησης (π.χ. από δύο goroutines) εκτελέσουν το `Query()` την ίδια στιγμή, μπορεί και οι δύο να διαπιστώσουν ότι δεν υπάρχει αντίδραση, εκτελώντας στη συνέχεια διπλό INSERT.
Σωστό! Αυτό ακριβώς είναι το κλασικό Race Condition. Χωρίς Transaction ή Atomic εντολή (UPSERT/ON CONFLICT), τα overlapping calls δεν είναι ασφαλή, παραβιάζοντας τον κανόνα της άσκησης που λέει "exactly one row". Η Go επιτρέπει εξαιρετικά γρήγορα concurrent αιτήματα, κάνοντας αυτό το σφάλμα σχεδόν βέβαιο να συμβεί.

Μόλις τελειώσεις, είσαι έτοιμος/η να δοκιμάσεις την άσκηση. Σκέψου το schema, σκέψου το UPSERT για το setReaction, και σκέψου το conditional COUNT (CASE WHEN) για την αναφορά. Καλή επιτυχία!
